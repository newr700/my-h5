# 1. 仓库与端口地图

| 仓库 | 角色 | 技术 | 端口 | 状态 |
|---|---|---|---|---|
| `my-h5-app` | 前端 | Vue3 + Vite + TS + Vant | dev 5173 / preview 4173 | 主力，持续开发 |
| `my-h5-server` | **Java 后端（新主力）** | Spring Boot 3.5 + MyBatis-Plus | **8080** | 刚建骨架 |
| `my-h5-api` | Node 后端 | Express + TS | 3000 | **冻结保留**——只作对照与退路，不再加功能 |

**裁定**：日常开发起「前端 5173 + Java 后端 8080」两个进程即可。Node 版不用启动。
前端通过代理访问后端：浏览器请求 `/api/xxx` → Vite 开发服务器转发到 `http://localhost:8080/xxx`（**去掉 `/api` 前缀**）。

> **为什么后端不配 `context-path=/api`？**（之前有过这个提议，现正式裁定为不配）
> ① 前端代理的 `rewrite` 去前缀逻辑已存在且工作正常，改端口只需一行；
> ② REST 惯例上 `/api` 前缀是**代理/网关层**的职责，不是应用的职责；
> ③ 后端路径保持干净（`/standings`），knife4j 文档页 `/doc.html`、健康检查 `/actuator/health` 与业务路径自然分开。
> 生产环境同理：Nginx 或网关做去前缀，应用本身不带。

# 2. 协作流程（两个人怎么不打架）

## 2.1 分支策略

- `main`：**受保护**，永远是可以跑的状态，不许直接 push；
- 干活一律开 `feature/功能名` 分支（如 `feature/order-create`）；
- 完成后发 Pull Request，**另一个人必须 review 通过**才能合入 main；
- review 看什么：契约有没有被破坏、分层红线有没有被违反、错误是否会被静默吞掉。

## 2.2 提交信息规范

格式：`类型(范围): 一句话说明`

| 类型 | 用于 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `refactor` | 重构（不改行为） |
| `chore` | 构建/依赖/杂项 |

示例：`feat(order): 创建订单接口含后端校验`

**裁定**：一次提交只做一件事。「顺手改了别的」是合并冲突的主要来源。

## 2.3 合并冲突时

先私下对齐「这块业务规则到底听谁的」，再改代码。**禁止用「两边都留着」的方式糊过去**。

# 3. Java 工程结构与分层红线

## 3.1 包结构（照此建包，不许发明新结构）

```
com.myh5.server
├── H5ServerApplication.java        ← 启动类，唯一
├── common/                         ← 全项目共享：Result、错误码、全局异常
├── config/                         ← 配置类：CORS、knife4j、Security（W3）
├── standings/                      ← 积分榜模块
│   ├── StandingsController.java
│   ├── StandingsService.java
│   ├── StandingsMapper.java        ← W1 数据层接入时建
│   └── entity/ dto/ vo/
├── order/                          ← 订单模块（同上结构）
└── user/                           ← 用户模块（同上结构）
```

**裁定**：按**业务模块**分包，不按「把所有 Controller 放一个包」的技术分层分包。
理由：一个模块的东西在一起，删模块就是删一个目录；两人各负责一个模块时互不干扰。

## 3.2 分层红线（对应前端的 views→stores→api→utils）

```
Controller → Service → Mapper → MySQL
```

- **Controller**：接参数、`@Valid` 校验、调 Service、返回 `Result`。❌ 不写业务逻辑，❌ 不碰 Mapper；
- **Service**：业务逻辑，`@Transactional` 只写在这一层。❌ 不碰 request/response；
- **Mapper**：只写 SQL。❌ 不含业务判断；
- 对象转换（Entity → VO）在 Service 完成，**Controller 不直接返回 Entity**（数据库结构不许泄漏给前端）。

## 3.3 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 类 | UpperCamelCase | `StandingsService` |
| 方法/字段 | lowerCamelCase | `getStandings()` |
| 常量 | UPPER_SNAKE_CASE | `MAX_PAGE_SIZE` |
| 数据库表 | snake_case 复数 | `orders`、`team_standings` |
| 数据库字段 | snake_case | `team_name`、`create_time` |
| Java 实体字段 | 与库字段对应的驼峰 | `teamName`、`createTime` |
| 接口路径 | 全小写 + `/` | `/order/create` |

**裁定**：下划线 ↔ 驼峰的映射交给 MyBatis 配置（`map-underscore-to-camel-case: true`），不手写 `@TableField` 逐个映射。

# 4. 接口契约（与前端签死的协议）

## 4.1 统一响应结构

```json
{ "code": 0, "message": "ok", "data": ... }
```

- `code = 0` 表示业务成功，其余全部为失败；
- 失败时 `data` 为 `null`，`message` 是给人看的一句话（前端直接 toast 它）；
- **Java 端用 `Result<T>` 类统一包装**（已建好，在 `common/Result.java`），Controller 返回值一律 `Result<XxxVo>`。

## 4.2 错误码表（全项目唯一，新增错误码先来这里登记）

| 码 | 含义 | 何时用 |
|---|---|---|
| `0` | 成功 | —— |
| `1000` | 未知错误 | 兜底的，能不用就不用 |
| `1001` | 参数校验失败 | `@Valid` 拦截到的非法入参 |
| `1002` | 资源不存在 | 查无此 id |
| `1101` | 未登录 / token 缺失或非法 | 受保护接口没带 token |
| `1102` | token 已过期 | 前端收到后跳登录页 |
| `1103` | 无权限 | 操作别人的资源（**故意与 1002 可混用**，防枚举时优先用后者） |
| `2001` | 用户名已存在 | 注册 |
| `2002` | 用户名或密码错误 | 登录（必须模糊，不区分哪种错） |
| `3001` | 订单不存在（或不是你的） | 取消/查看订单 |
| `3002` | 订单当前状态不允许该操作 | 对 paid/closed 订单执行取消 |
| `5000` | 系统内部错误 | 未捕获异常兜底 |

**裁定**：业务失败**不抛 HTTP 500**——HTTP 状态码保持 200，成败由 `code` 表达（前端拦截器就是这么写的，契约一致）。HTTP 4xx/5xx 只留给框架级错误。

## 4.3 通用约定

| 项 | 裁定 |
|---|---|
| 分页参数 | `pageNum`（从 **1** 开始）、`pageSize`（默认 **10**，上限 **50**，超出按 50） |
| 分页响应 | `{ list, total, pageNum, pageSize }` |
| 时间格式 | 字符串 `"yyyy-MM-dd HH:mm:ss"`，东八区；Jackson 全局配置，不逐个加注解 |
| 金额 | **整数，单位分**。数据库 `BIGINT`，Java `Long`。**禁止** `float/double`（浮点会丢精度：`0.1+0.2≠0.3`） |
| 字符串空值 | 可空字段返回 `''` 而不是 `null`（前端契约就是这么假设的，如 `logoUrl`） |
| 布尔 | 数据库 `TINYINT(1)`，Java `Boolean`，JSON `true/false` |

## 4.4 接口清单（全部路径在此，新增接口先登记再写代码）

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| GET | `/standings` | 积分榜（20 条，后端排好序） | 公开 |
| GET | `/order/list?pageNum=&pageSize=` | 我的订单列表 | 登录 |
| POST | `/order/create` | 创建订单 `{title, quantity, unitPrice}` | 登录 |
| POST | `/order/cancel` | 取消订单 `{id}` | 登录 |
| POST | `/user/register` | 注册 `{username, password, nickname}` | 公开 |
| POST | `/user/login` | 登录 `{username, password}` → `{token, user}` | 公开 |
| GET | `/user/profile` | 我的资料 | 登录 |
| GET | `/actuator/health` | 探活（框架自带） | 公开 |

# 5. 数据库规范（W1 建表时逐条照做）

| 项 | 裁定 |
|---|---|
| 引擎 / 字符集 | InnoDB / `utf8mb4`（能存 emoji 的那个，不是 `utf8`） |
| 主键 | `id BIGINT UNSIGNED AUTO_INCREMENT`。**不用 UUID/雪花**——数据量用不上，自增简单且面试能讲清页分裂 |
| 公共字段 | 每张表都有 `create_time`、`update_time`（由 MyBatis-Plus 自动填充，代码不手动 set）、`deleted TINYINT(1) DEFAULT 0`（逻辑删除，`@TableLogic`） |
| 删除 | **一律逻辑删除**（UPDATE deleted=1）。物理 DELETE 语句在本项目禁止出现 |
| 建表方式 | **只通过 Flyway 迁移脚本**（`V1__init.sql` 起，版本号递增，文件只追加不修改）。禁止手动连数据库改表——改了别人和环境都对不上 |
| 字段注释 | 每个字段写 `COMMENT`，三个月后自己看得懂 |

# 6. 环境、配置与密钥

- 配置走 `application.yml` + `application-dev.yml` / `application-prod.yml` 两个 profile；
- **数据库密码、JWT 密钥只放环境变量**（`SPRING_DATASOURCE_PASSWORD`、`JWT_SECRET`），配置文件里写 `${JWT_SECRET:}` 占位，**真实值永不进 Git**；
- `.gitignore` 已含 `application-local.yml`——你想在本地存真实密码，就放这个文件；
- 后端是**运行时读取**环境变量（改完重启生效），和前端**构建时注入**（改完必须重新 build）不同，别搞混。

跑 Maven 用 **Windows 自带的 PowerShell 或 Windows Terminal**。Maven 在 `D:\dev\tools\build\apache-maven-3.9.12`，JDK 是 Temurin 17.0.4.1。

# 7. 代码内部规范

## 7.1 注释

- 只写「**为什么**」，不写「这是什么」（`// 循环遍历列表` 是废话）；
- 沿用现有约定：`[清单条目] 做了什么 —— 为什么`，技能点标 `(技能点：xxx)`；
- 每个 Controller 类上一行 Javadoc：这个模块是干什么的 + 对应 PRD 的功能编号（如 `对应 PRD-F1`）。

## 7.2 异常处理

- 业务异常：throw `new BizException(3002, "当前订单状态不可取消")`，由全局异常处理器转成 `Result`；
- **禁止** `catch (Exception e) {}` 空 catch（静默吞错是本项目头号禁止事项，前端时代就立过这条规矩）；
- 未捕获异常 → 全局处理器兜底返回 `5000`，同时**打日志**（`log.error`，带堆栈）。

## 7.3 日志

- 用 `log.info/warn/error`（Lombok `@Slf4j`），**禁止 `System.out.println`**；
- 关键动作打日志：创建订单、取消订单、登录失败。带上业务 id（如订单号），不带密码/token。

## 7.4 TODO

格式：`// TODO(名字-日期): 什么事`，如 `// TODO(阿zb-1004): F6 完成后改为从 token 取用户`。
离职式的裸 `// TODO` 不许提交。

# 8. 依赖引入原则（延续 ADR-001 的教训）

1. **按阶段引入**：骨架阶段只有 web/validation/actuator/knife4j/lombok；MyBatis-Plus/MySQL/Flyway 在 W1 数据层接入时再加；Security/jjwt 在 W3 再加。一次引入一堆用不上的依赖，排查冲突时哭都来不及；
2. **引入前必查维护状态**：最后一次发版时间、是否有活跃 fork、与 Spring Boot 3.5 的兼容性；
3. 版本号统一写在 `pom.xml` 的 `<properties>` 里，不散落在各处。

# 9. 常见疑问 Q&A（提前裁定的模棱两可）

**Q：接口风格要 RESTful 吗（PUT/DELETE/PATCH）？**
A：不用。**写操作一律 POST**，路径动宾结构（`/order/create`、`/order/cancel`），读操作一律 GET。理由：契约已经和前端对齐，不折腾；面试被问就说「团队约定简化风格，一致性优先」。

**Q：排序在前端还是后端做？**
A：**后端**。积分榜的 rank 由后端生成。原则：谁拥有数据谁负责顺序，前端只渲染。

**Q：金额计算在哪做？**
A：**后端**。前端传的单价/数量只作参考输入，总价后端重算。任何「信前端传来的计算结果」的做法都是漏洞。

**Q：Entity 能直接返回给前端吗？**
A：不能。过一道 VO。理由：数据库字段（密码散列、deleted、内部 id）不许泄漏；表结构变了不影响前端。

**Q：写 SQL 还是用 MyBatis-Plus 的方法？**
A：单表 CRUD 用 Plus；**多表/聚合/复杂条件手写 XML**（这是定死的项目约定，保住 SQL 手感）。

**Q：发现文档（PRD/手册）和代码不一致？**
A：**以文档为准改代码**，除非你认为文档错了——那就走 PRD 第 6 章的变更流程，先改文档。

**Q：能用 AI 生成代码吗？**
A：能，但**每一行都要能讲出为什么**。讲不出的代码不许进仓库。面试时这段代码就是你写的。

**Q：MySQL 装不上/没有怎么办？**
A：先报告，不要自己换成 H2/SQLite 凑合——那会让交付物和文档不一致。项目经理会决定解决方案（装 MySQL / Docker / 云库免费层）。

# 10. 员工开工清单（第一天照此执行）

1. 读完《PRD-项目需求文档》和本手册（约 30 分钟）；
