# Web 项目全考量清单（新手参考版）

> 这份清单回答一个问题：**一个 Web 项目从想法到上线再到迭代，总共要考虑哪些事。**
> 绿色勾 = 本项目已覆盖；黄色半勾 = 部分覆盖；方框 = 还没涉及，动手前要讨论。
> 用法：不是一次做完，是每个阶段开工前把对应分区过一遍。

## 先纠正一个思维模型（写给从 C 语言过来的我们）

把前后端看成"两个大函数靠参数联系"——对了一半。对的部分：请求＝传参，响应＝返回值。
不对的部分有五条，每条都是 C 世界隐含假设的崩塌：

1. **传的不是引用，是文本复印件。** HTTP 传输的是序列化后的 JSON 文本，双方各持一份拷贝。
   后端"改完"必须把新文本寄回来（响应），前端拿到还要自己解析。这就是为什么需要"契约"。
2. **调用不是同步阻塞的。** `await` 把函数冻结在那一行、让出主线程（像注册回调后继续跑主循环，不是死等）。
3. **调用可能根本到不了。** 断网、超时、500 随时发生。每个请求必须写失败分支，
   等价于 C 里检查 `malloc` 返回 NULL 的自觉。
4. **没有编译器跨边界查类型。** 前端 TS 和后端 TS 是两个独立编译单元，互相看不见。
   `types/api.ts` + 运行时校验（`utils/validate.ts`）就是我们手写的"边界编译器"。
5. **程序不是跑一次就结束，也不是单用户。** 后端是 `while(1){accept(); handle();}` 的守护进程；
   HTTP 无状态，每个请求都是初次见面——所以才需要 token（自带身份）和数据库（服务器记的笔记）。

**万能三问**：拿到任何 Web 新概念，先问——它跑在哪台机器上？什么时候生什么时候死？数据怎么到我手里？

## 0. 需求与设计（写代码之前）

- [x] 明确目标用户与核心场景：谁在什么情况下用这个页面，一句话说得出
- [ ] 页面清单与路由规划：先列全所有页面再动手，免得边写边加
- [x] 接口契约先行：路径、入参、返回字段先定死（`types/api.ts` 是镜像）
- [ ] 数据模型设计：接数据库前先画表——有什么实体、实体之间什么关系
- [x] 设计稿或草图：哪怕是手画的，两人认知才能对齐

## 1. 前端

- [x] 目录与模块分区：共享区收敛，业务按模块纵向切
- [x] 移动端适配：vw 方案；后续注意刘海安全区、1px 边框问题
- [ ] 路由懒加载：页面多了以后按需加载，减小首屏体积
- [ ] 列表三态：加载中 / 空数据 / 请求失败，每个列表页都要有（standings 已示范）
- [ ] 表单校验与防重复提交：提交中禁用按钮；前端校验是体验，后端校验才是安全
- [ ] 构建优化：分包、gzip、图片压缩、组件按需引入
- [x] 环境变量管理：dev / prod 的 baseURL 分开

## 2. 后端

- [ ] 分层结构：routes（收请求）→ services（业务）→ data（数据），已有 routes/data，缺 services
- [ ] 入参校验：后端必须自己再验一遍，**绝不信任前端**——攻击者可以绕过页面直接发请求
- [ ] 统一错误码：外壳 `{code, message, data}` 有了，错误分类还要细化（1xxx 参数错、2xxx 鉴权错…）
- [ ] 数据库与迁移：MySQL + Prisma；表结构变更走迁移文件，可追溯可回滚
- [ ] 鉴权：登录签发 token、每个受保护接口校验 token、过期刷新
- [ ] 日志：每个请求记一行（谁、什么时间、哪个接口、多久、成功否），出问题才有得查
- [ ] 限流防刷：同一 IP 高频请求要拦

## 3. 通信与安全

- [x] 开发期代理解决跨域：vite proxy 已配（生产环境用同域部署或后端开 CORS）
- [ ] HTTPS：上线必须，本地开发不需要
- [ ] 密码存储：哈希 + 盐（bcrypt），**绝不能明文入库**
- [ ] XSS 防护：用户输入的内容渲染前转义，不随意 `v-html`
- [ ] CSRF 防护：理解 token 方案为什么能缓解它
- [ ] SQL 注入防护：永远用参数化查询，永远不拼 SQL 字符串
- [x] 密钥管理：`.env` 不入库，真实密钥只放服务器

## 4. 工程协作

- [x] Git 分支模型：main 保护 + feature 分支，PR 合并
- [x] Commit 规范：Conventional Commits
- [x] Lint 与格式化：ESLint + Prettier，机器管住风格，人不吵架
- [ ] Code Review 流程：互看 5 分钟也算，贵在坚持
- [ ] CI 自动构建：提交后自动跑 lint + build + 测试，坏了当场知道
- [ ] Mock 并行开发：用 Apifox 定契约，前端拿 mock 开发不等后端

## 5. 测试

- [ ] 单元测试：vitest 测 utils 和 stores（校验函数最值得先测）
- [ ] 接口测试：现在手动 curl，应该脚本化固化下来
- [ ] E2E 测试：Playwright 模拟用户真实点击
- [ ] 多机型多浏览器：iOS / Android / 微信内置浏览器都要过一遍

## 6. 部署运维（上线那一刻）

- [ ] 域名与备案：国内服务器需要 ICP 备案（周期以周计，提前办）
- [ ] 前端静态托管：`dist/` 丢到 nginx / 对象存储 / CDN
- [ ] 后端进程守护：pm2 让后端崩溃自动重启、开机自启
- [ ] 环境隔离：dev / prod 变量有了，还差独立测试环境
- [ ] 数据库备份：定时备份；先想清楚"数据丢了怎么办"再上线
- [ ] 监控与错误上报：Sentry 之类；用户不说，你永远不知道页面挂了
- [ ] 回滚方案：新版本坏了，多久能回到上一版？先演练一次

## 7. 上线之后

- [ ] 数据统计：埋点看用户实际怎么用（和你们以为的往往不一样）
- [ ] 用户反馈渠道：给用户留个说话的地方
- [ ] 迭代计划：按使用数据决定下个版本做什么，而不是拍脑袋

## 给我们的学习路径建议（按优先级）

1. **先把"列表三态 + 表单"跑通**——这是业务代码里出现频率最高的两个模式
2. **接数据库 + 后端鉴权**——理解"无状态 HTTP + token + 持久化"铁三角
3. **加单元测试**——校验函数（validate.ts）是最佳起点，逻辑纯粹、容易断言
4. **走一遍部署**——哪怕部署到一台最便宜的服务器，HTTPS、pm2、备份都会逼你理解"环境"的概念
5. 安全项（XSS/CSRF/注入）在写用户输入功能之前必须看
