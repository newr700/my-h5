# 1. 项目背景与目标

## 1.1 一句话说明

一个足球主题的 **Web 应用**：手机端为主、PC 端同样可用，包含**积分榜浏览、用户体系、球票订单**三个模块。

## 1.2 做这个项目的真实目的

它是一份**实习面试作品**。因此所有决策都要服务两个问题：

1. 面试官追问「为什么这么做」时，我们有答案；
2. 面试官说「打开我看看」时，有一个能点开的链接。

**凡是不能服务这两个目标的「锦上添花」，一律不做。** 这是本项目最重要的取舍原则。

## 1.3 成功的定义（验收的总开关）

- 有一个公网可访问的链接，手机和电脑打开都正常；
- 数据存在真实数据库（MySQL）里，重启不丢；
- 至少有一个完整的「写操作闭环」（创建订单：表单 → 校验 → 落库 → 列表刷新）；
- 有注册/登录，受保护接口无 token 不可访问；
- README 能在 30 秒内让面试官明白这是什么项目、亮点在哪。

# 4. 功能详述（业务规则全部在此裁定，照做即可）

## F1 积分榜列表

**用户故事**：作为访客，我想看到 20 支球队的实时积分排名，以便了解联赛形势。

**业务规则（裁定，不许改动）**：

- 积分榜共 **20 支球队**，数据由初始化脚本灌入，不提供「录入比赛结果」功能；
- 积分规则：**胜 3 分、平 1 分、负 0 分**；
- 排序规则（严格按此顺序，逐级比较）：
  1. 积分高者在前；
  2. 积分相同 → **净胜球**（进球 − 失球）多者在前；
  3. 净胜球相同 → **进球数**多者在前；
  4. 仍相同 → 按**队名拼音/字典序**排。
- **排序和 `rank`（排名序号）由后端生成**，前端拿到什么顺序就显示什么顺序，前端不排序；
- 返回字段严格对齐前端契约（这是和前端签死的，一个字都不能改）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `rank` | number | 排名 1–20 |
| `teamName` | string | 队名 |
| `played` | number | 已赛场次 |
| `win` / `draw` / `lose` | number | 胜/平/负场次 |
| `goalsFor` / `goalsAgainst` | number | 进球/失球数 |
| `points` | number | 积分 |
| `logoUrl` | string | 队徽地址；**没有就给空字符串 `''`，不能给 null**（前端靠它判断显示图片还是排名圆圈） |

> ⚠️ 注意：契约里**没有** `goalDiff`（净胜球）字段——它只参与后端排序，不下发。
> 也**没有** `id` 字段。不要自作主张加字段，加了前端也不会用，还会污染契约。

**验收标准**（逐条打勾才算完成）：

- [ ] 接口返回恰好 20 条，顺序符合排序规则；
- [ ] `logoUrl` 为空字符串时页面显示排名圆圈，不裂图；
- [ ] 下拉刷新（手机）/ 刷新按钮（PC）能重新拉取；
- [ ] 接口挂掉时页面显示错误态并可重试（前端已有，联调验证）。

## F2 用户主页

**用户故事**：作为注册用户，我想看到自己的资料。

- 字段：`id`、`nickname`、`avatar`（与前端契约一致）；
- **F6 完成前**：返回一个固定的演示用户（和现在 Node 版行为一致）；
- **F6 完成后**：从 token 解析出用户身份，返回真实用户资料。

## F3 订单列表

**用户故事**：作为注册用户，我想看到自己下过的球票订单。

- 只返回**当前登录用户**的订单（F6 前返回演示数据）；
- 列表按创建时间**倒序**（最新的在前）；
- 分页：参数 `pageNum`（从 1 开始）、`pageSize`（默认 10，上限 50，超过按 50 算）；
- 每条至少包含前端契约字段：`id`、`title`、`amount`、`status`；**允许**额外返回 `orderNo`、`quantity`、`unitPrice`、`createTime`（后端返回字段 ⊇ 前端需要的字段，前端解析是宽松的，多给不会崩）。

## F4 创建订单（本项目的核心写操作）

**业务定义**：订单 = **球票购买记录**。用户选择一场比赛（用文字描述即可）、票数，生成订单。

**字段规则**：

| 字段 | 规则 |
|---|---|
| `orderNo` | 后端生成，格式 `ORD` + `yyyyMMdd` + 6 位随机数（如 `ORD20261004837261`），全局唯一 |
| `title` | 用户填写，非空，≤ 50 字（如「曼城 vs 阿森纳 · 10 月 12 日主场」） |
| `quantity` | 整数，**1–10** 张 |
| `unitPrice` | 整数，**单位：分**（1 元 = 100 分），范围 1–100000（即最高 1000 元） |
| `amount` | **后端计算**：`quantity × unitPrice`，**不信前端传的总价** |
| `status` | 创建时固定为 `pending` |

**校验规则（前后端必须各做一遍）**：

- 前端校验：为了**体验**——用户输错立刻提示，不用等网络往返；
- 后端校验：为了**安全**——用 curl/Postman 直接打接口可以绕过前端，后端必须重新校验全部规则，任何一条不过就返回错误码 `1001` 和具体原因。

**验收标准**：

- [ ] 合法提交后订单落库，列表页刷新能看到新订单；
- [ ] 数量为 0、11、负数，单价为 0、负数、小数，标题为空/超长 → 前后端都拒绝；
- [ ] 用 curl 直接发非法请求 → 后端返回 `1001` 而不是 500；
- [ ] 连续快速点两次提交按钮 → 前端按钮在请求期间禁用，不产生两笔订单（前端防重，后端本次不做幂等，是已知简化，写进 README）。

## F5 取消订单

- 只有 **`pending`（待支付）** 状态的订单可以取消；
- 取消 = 状态改为 `closed`，**不是删除记录**；
- 对 `paid` 或已是 `closed` 的订单调用取消 → 返回错误码 `3002`；
- 只能取消**自己的**订单，取消别人的 → 返回错误码 `3001`（故意不区分「不存在」和「别人的」，避免试探出别人的订单号，这叫防枚举）。

**订单状态机（唯一合法流转）**：

```
pending ──支付(本次不实现真实支付，预留)──▶ paid
   │
   └──取消──▶ closed（终态，不可再变）
```

- `paid` 不可取消（退款流程不做，见第 7 章边界）；
- `closed` 是终态，任何操作都返回 `3002`。

## F6 注册 / 登录（JWT）

**注册**：

| 字段 | 规则 |
|---|---|
| `username` | 4–20 位，只允许字母、数字、下划线，全局唯一（不区分大小写） |
| `password` | 8–32 位，必须同时包含字母和数字；**BCrypt 加密存储，数据库里绝不允许出现明文** |
| `nickname` | 1–20 位，任意字符 |

- 用户名已存在 → 错误码 `2001`；
- 不做邮箱/手机验证码（简化，见边界）。

**登录**：

- 成功 → 返回 JWT token + 用户资料；
- 失败 → 统一返回 `2002`「用户名或密码错误」。**必须模糊**：不能告诉调用方到底是用户名不存在还是密码错了（防止批量探测有哪些用户名，这叫防枚举，面试考点）；
- 不做登录失败锁定（简化，已知取舍）。

**token 规则**：

- JWT，有效期 **2 小时**，过期后所有受保护接口返回 `1102`，前端跳回登录页（简化：不做 refresh token）；
- 前端存 `localStorage`（XSS 风险的取舍单独写 ADR）；
- 受保护接口：创建订单、取消订单、订单列表、用户主页。积分榜保持公开。

## F8 部署上线

- 前端 → Vercel；后端 → 云服务器（或 Render 免费层）；数据库 → 云托管 MySQL；
- 验收标准：把链接发给任何一部手机，能注册、登录、下单、取消，全流程走通。

# 5. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 本地接口响应 < 500ms；线上冷启动除外（免费层特性，演示前先唤醒） |
| 兼容 | 手机（iOS Safari / 安卓 Chrome）和 PC（Chrome / Edge）都可用，768px 为断点 |
| 安全 | 密码 BCrypt；SQL 全部 `#{}` 预编译；生产关闭接口文档页；CORS 白名单 |
| 数据 | 所有表有创建/更新时间；删除一律逻辑删除；金额一律整数（分） |

# 7. 明确不做什么（边界，防止范围蔓延）

以下功能**被问起来就说"不做"**，这不是偷懒，是范围控制：

- ❌ 真实支付对接（微信/支付宝）——`paid` 状态仅预留
- ❌ 退款流程
- ❌ 后台管理系统（管理员页面）
- ❌ 录入比赛结果、自动计算积分
- ❌ 实时推送 / WebSocket
- ❌ 邮箱/手机验证码、找回密码
- ❌ 登录失败锁定、refresh token
- ❌ 多语言、深色模式

> 面试时这份「不做什么」清单本身就是加分项：**能划清边界的产品经理思维，比堆功能值钱**。
