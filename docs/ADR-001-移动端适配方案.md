# ADR-001：移动端适配方案选型

> ADR = Architecture Decision Record（架构决策记录）。
> 作用是**把"为什么选它、风险是什么、什么时候该换"固定下来**，
> 免得半年后没人记得当初为什么这么干，也没人敢动。
> 这是资深工程师和新手的分水岭之一：**选型不记录，等于没选型。**

## 状态

- 当前方案：`postcss-px-to-viewport-8-plugin@1.2.5`
- 健康度：**黄灯**（可用，但上游已停更 2 年+）
- 复核触发条件：需要在平板/PC 上限制最大宽度时，或该插件与新版 Vite/PostCSS 冲突时

## 上下文（要解决什么问题）

项目是移动端 H5，设计稿按 375px 宽出图。需要一套方案让"按设计稿抄像素值"就能在所有手机上等比缩放，且**不增加新人写样式时的心智负担**。

## 候选方案与当初的取舍

| 方案 | 优点 | 缺点 | 当时判断 |
| --- | --- | --- | --- |
| **px → vw（构建期替换）** | 写 px 即所见，零运行时开销，配置一处 | 平板/PC 上会无限放大；依赖一个构建插件 | ✅ 选中 |
| rem + JS 动态设根字号 | 能限制最大宽度；老牌方案 | 需要运行时脚本，首屏有闪烁风险 | 备选 |
| 全靠媒体查询手写 | 无依赖 | 工作量大，两人项目写不起 | 淘汰 |

## 决策

选 **px→vw 构建期替换**，具体实现用社区 fork `postcss-px-to-viewport-8-plugin`，而不是原版 `postcss-px-to-viewport`。

理由（当时的判断依据）：

1. **原版确实死了**：`postcss-px-to-viewport@1.1.1` 最后更新 2024-02，基于 PostCSS 7 的 `postcss.plugin` API —— 在 PostCSS 8 下会直接报弃用警告，插件作者自己的仓库也已归档。
2. **fork 版兼容 PostCSS 8**：`postcss-px-to-viewport-8-plugin@1.2.5` 是社区维护的 PostCSS 8 适配版，Vite 生态里大量项目在用。
3. **对新手友好**：只改一处配置，写代码时不用换算，符合"让你们专心写业务逻辑"的目标。

## 我当初没做对的地方（复盘）

选型的**技术判断是对的**（避开死掉的 upstream、挑兼容版），但**风险管理是不到位的**：

- 没检查上游维护状态并写进文档 —— 这是架构师的本职工作，不是加分项
- 没在代码里留下"这个依赖有风险 + 将来怎么换"的线索，等于把隐患留给了半年后的自己
- 没提前说明该方案的固有缺陷：**纯 vw 在平板和 PC 上会无限放大**（375 稿上一个 300px 宽的卡片，在 iPad 上会变成 768px）

## 迁移路径（需要时按此执行）

**触发条件：需要支持平板/PC，或插件与新版构建工具冲突。**

1. `npm uninstall postcss-px-to-viewport-8-plugin`
2. `npm i -D postcss-mobile-forever`（活跃维护，2025-03 仍有更新）
3. 改 `vite.config.ts` 这一段配置，主要新增 `maxDisplayWidth` 之类的最大宽度限制
4. 业务代码 `.vue` 里的样式**一行都不用动** —— 这就是"逃生成本极低"的含义

**为什么迁移这么便宜**：这个插件只做构建期文本替换，产物是纯 CSS；它既不在运行时执行，也不要求业务代码配合（没有 import、没有 API 调用）。对比一下：如果当初选了一个要求你在组件里写 `useResponsive()` 的库，迁移就得改几十个文件。

## 通用方法：怎么判断一个依赖还活着（技能点：依赖评估）

选任何第三方库前，花 3 分钟做这四项体检：

1. **最后发版时间**：`npm view <包名> time.modified`。超过 18 个月没动静 → 黄灯
2. **是否被标记废弃**：`npm view <包名> deprecated`。有值就是官方劝退
3. **issue 是否有人回**：打开 GitHub Issues，看 maintainer 最近一次回复是什么时候
4. **逃生成本有多高**（最关键的一条）：
   - 只在构建期生效 / 只做文本替换 → 低，随时可换
   - 需要业务代码 import 它、按它的 API 写逻辑 → 高，选型要格外慎重
   - 结论：**越是被业务代码深度依赖的库，越要挑活跃的。**
