# 第零部分：换语言的代价先说清楚

## 0.1 换的是什么、不换的是什么

**不换的（这是本次决策最重要的约束）**：

- 前端 Vue3 项目**一行不改**
- 前后端之间的**数据契约不变**：仍然是 `{ code, message, data }`
- 接口路径不变：`/standings`、`/order/list`、`/user/profile`、`/health`

之所以能这么干净，是因为后端对前端而言**只是一个 URL**。前端从来不知道后面跑的是 Node 还是 Java——这就是我们一开始定「只通过 HTTP 通信」换来的红利。现在它兑现了。

**要换的**：

| 项 | 原（Node） | 现（Java） |
|---|---|---|
| 运行时 | Node.js 进程 | JVM 进程 |
| 框架 | Express 5 | Spring Boot |
| 语言 | TypeScript | Java |
| 构建 | npm + tsc/tsx | Maven |
| 产物 | `dist/index.js` | `target/*.jar`（内嵌 Tomcat 的可执行 jar） |
| 默认端口 | 3000 | **8080** |
| 数据访问 | Prisma（原计划） | MyBatis-Plus |

## 0.2 顺带解决掉一个旧隐患

上一版文档里我记录了一个「会让生产环境跑不起来」的问题：后端的 `noEmit: true` + `start` 依赖 `tsx`，而 `tsx` 在 devDependencies 里，生产安装时会被排除。

**换成 Java 后这个问题自动消失了**——因为 Java 是编译型语言：`mvn package` 产出一个完整的 jar，运行时只需要 JRE（Java 运行环境），不存在「运行时才去解释源码」这回事。这是换 Java 的一个附带的、实实在在的收益。

## 0.3 换 Java 要付出的代价（诚实列出）

1. **本地内存占用变大**：Spring Boot 空载大约占 200–400 MB 内存，Node 进程只有几十 MB。
2. **启动变慢**：Node 秒起；Spring Boot 要 3–10 秒（JVM 启动 + Spring 容器初始化）。开发时改一次代码要重启一次，比 `tsx watch` 的热更新体验差。
3. **冷启动更明显**：部署到免费平台后休眠，首次访问等待时间会更长。
4. **免费部署层更吃紧**：免费容器常给 512 MB 内存，跑 Java 需要调 JVM 参数（后面 4.4 节讲）。
5. **开发代理目标要改**：`vite.config.ts` 里 `/api` 转发目标从 3000 改成 8080。

# 第一部分：技术栈选型总表

> 阅读方式：**「解决什么」** 是它的职责，**「为什么选它」** 是它被选中的理由，**「为什么不选 X」** 才是真正体现架构判断的地方。

## 1.1 语言与运行时

| 项 | 选型 | 解决什么 | 为什么选 / 为什么不选别的 |
|---|---|---|---|
| **JDK**【选型】 | **Java 17**（本机已装 Temurin 17.0.4.1） | 编译和运行 Java 程序的环境 | ✅ **本机已有**，零安装成本；✅ LTS（长期支持版）；✅ Spring Boot 3.x 和 4.x **都要求 Java 17 为最低版本**，选它两条路都走得通<br>⚠️ 企业新项目越来越常见的是 **Java 21**（虚拟线程、更多新语法）。**升级触发条件**：你愿意装一个 JDK 21 → 建议直接上 21，面试时"虚拟线程"是很好的加分话题。不装也能正常做 |
| 构建工具 | **Maven 3.9.12**（本机已装） | 管依赖、编译、打包、跑测试 | ✅ 国内企业**绝对主流**，面经/教程默认就是它；✅ `pom.xml` 声明式，依赖版本集中管理<br>❌ 不选 Gradle：构建更快、语法更灵活，但国内 Java 岗默认 Maven，且 Groovy/Kotlin DSL 对新手是额外负担 |

> **⚠️ 本机环境坑（已实测）**：这台机器的终端里跑 `mvn` 会失败，报 `dirname: command not found` 和 `ClassNotFoundException: plexus.classworlds.launcher.Launcher`。**不是 Maven 装坏了**，是终端缺 `uname`/`dirname` 等基础命令导致 Maven 启动脚本算不出自己的安装路径。**用系统自带的 PowerShell 或 Windows Terminal 跑 Maven 就正常**。

## 1.2 核心框架

| 项 | 选型 | 解决什么 | 为什么选 / 为什么不选别的 |
|---|---|---|---|
| **Spring Boot**【分歧·重点】 | **3.5.x**（3.x 最后一条线） | 把 Spring 的繁琐配置收敛成「约定大于配置」：内嵌服务器、自动装配、开箱即用的生产特性 | 见 2.1 节的完整论证，**这是全篇最需要你理解的一个决策** |
| Web 层 | **Spring Web MVC**（`spring-boot-starter-web`） | 处理 HTTP 请求：路由、参数绑定、JSON 序列化 | ✅ 同步阻塞模型（一个请求一个线程），和 Express 的心智模型一致，你最容易理解；✅ 国内绝大多数业务项目是 MVC<br>❌ **不选 WebFlux**（响应式/异步非阻塞）：性能上限高，但调试难度陡增、生态（尤其 MyBatis）支持弱。**实习阶段不该碰** |
| JSON 序列化 | **Jackson**（Spring Boot 内置） | Java 对象 ⇄ JSON 的互相转换 | 不用单独选，Spring Boot 默认就是它。<br>⚠️ 注意：**Spring Boot 4 换成了 Jackson 3**（包名从 `com.fasterxml` 变成 `tools.jackson`），这也是我倾向 3.5 的原因之一 |

## 1.3 数据层

| 项 | 选型 | 解决什么 | 为什么选 / 为什么不选别的 |
|---|---|---|---|
| **ORM**【选型】 | **MyBatis-Plus 3.5.17** | 数据库表和 Java 对象之间的映射；SQL 的执行与结果封装 | 见 2.2 节完整论证（你学过 MyBatis，这里重点讲 Plus 的取舍） |
| 数据库 | **MySQL 8.0** | 真正持久化存储数据 | ✅ 国内**绝对主流**，Java + MySQL 是黄金组合；✅ 面试默认考 MySQL（索引、事务、锁、执行计划），你学的每一分都直接变现；✅ 与 MyBatis-Plus 配合最成熟<br>❌ 不选 SQLite：Java 项目用它显得像玩具，且文件库在容器里会丢<br>❌ 不选 PostgreSQL：很好，但国内 Java 岗面试围绕 MySQL 展开的比例高得多 |
| 连接池 | **HikariCP**（Spring Boot 默认） | 复用数据库连接（建连接很贵，不能每次请求都新建） | ✅ Spring Boot 默认集成、性能最好、零配置<br>替代方案 Druid（阿里）卖点是**自带 SQL 监控页面**，但多一个依赖、多一个要防护的端点。默认选 Hikari |
| 数据库迁移 | **Flyway** | 表结构变更的**版本化管理**（谁在什么时候改了哪张表，可追溯可回滚） | ✅ 每个版本就是一个 `.sql` 文件，直观、新手友好；✅ 国内使用率高于 Liquibase<br>❌ Liquibase：用 XML/YAML 描述变更，跨库能力强但学习成本高<br>📌 **这是面试加分项**：很多应届生项目是手写建表 SQL、改一次就重来一次，你能讲「迁移有版本号、只追加不修改」立刻拉开差距 |

## 1.4 接口与校验

| 项 | 选型 | 解决什么 | 为什么选 / 为什么不选别的 |
|---|---|---|---|
| **接口文档**【选型】 | **knife4j 4.5.0**（`knife4j-openapi3-jakarta-spring-boot-starter`） | 自动生成在线接口文档，**还能直接在页面上发请求调试** | ✅ 你学过，零学习成本；✅ 中文界面、国内企业普及率极高；✅ 演示时把文档页甩给面试官看，比口头描述接口强得多<br>⚠️ 三个必须知道的坑见 2.3 节（坐标选错会启动失败、生产必须关闭等） |
| 底层文档规范 | **springdoc-openapi**（knife4j 自带） | 按 OpenAPI 3 规范扫描注解生成文档 | knife4j 本质是 **springdoc 的增强 UI**（换皮 + 加功能），注解用的是 OpenAPI 3 标准的 `@Tag` `@Operation`。**别再去找 Springfox 了**——它已停更，且不支持 Spring Boot 3 |
| 参数校验 | **Hibernate Validator**（`spring-boot-starter-validation`） | 用注解声明校验规则：`@NotNull` `@NotBlank` `@Size` `@Pattern` | ✅ 这就是**「前后端双校验」里后端那一半**的标准实现；✅ 与全局异常处理器配合，校验失败自动返回统一格式错误<br>📌 C 类比：它相当于在函数入口处统一做**参数合法性断言**，只不过断言条件是写在参数声明上的，不用手写一堆 `if` |
| 统一响应 + 全局异常 | **`@RestControllerAdvice` + `@ExceptionHandler`** | 把所有异常的返回格式收敛成 `{code,message,data}` | ✅ 对应原来 Express 的统一响应外壳；✅ 业务代码只管 `throw`，不用到处 try-catch<br>📌 这是最能体现「工程化」的一处：没有它，每个 Controller 都要自己写 try-catch，漏一个就返回一堆堆栈给前端 |

## 1.5 安全

| 项 | 选型 | 解决什么 | 为什么选 / 为什么不选别的 |
|---|---|---|---|
| **鉴权框架**【选型】 | **Spring Security 6** | 身份认证（你是谁）+ 授权（你能干什么） | ✅ 面试高频核心区：过滤器链、`FilterChainProxy`、认证/授权分离、Session vs JWT、CSRF——**这些话题的价值远超"自己写个拦截器"**；✅ `BCryptPasswordEncoder` 现成可用；✅ 后续加角色权限几乎零成本<br>⚠️ 代价：学习曲线陡。对策见 2.4 节（只用最小配置，不开 formLogin/session） |
| Token | **JWT（jjwt 0.12.x）** | 登录态凭证（无状态，服务端不存 session） | ✅ 前后端分离 + 跨域场景下最主流；✅ 0.12.x 才适配 Java 17（0.11.x 在 JDK 17 上会因 JAXB 缺失报错）<br>📌 备选：Spring Security 自带 `spring-security-oauth2-jose`（Nimbus）可**校验** JWT，但**签发**仍需自己写。统一用 jjwt 更简单 |
| 密码存储 | **BCrypt**（Spring Security 自带） | 把明文密码变成不可逆的散列值 | ✅ 自带随机盐（salt），同一个密码每次存出来都不一样；✅ 计算慢，专门对抗暴力破解<br>❌ **绝不能用 MD5/SHA**——它们是为「快」设计的，彩虹表一查就破。这是面试必考题 |

## 1.6 工具与工程

| 项 | 选型 | 解决什么 | 为什么选 / 为什么不选别的 |
|---|---|---|---|
| **工具库**【选型】 | **Hutool** | 日常杂活：字符串、日期、加解密、HTTP 调用、Bean 拷贝 | ✅ 你学过；✅ 国内普及率极高，写业务代码快<br>⚠️ **面试提示**：说「我用了 Hutool」本身不加分，甚至可能被认为只会调 API。**要能说清你用它哪一块、底层原理是什么**（比如 `SecureUtil.md5()` 背后就是 `MessageDigest`）。部分公司禁用它，要求用 Guava / Apache Commons——知道这些替代品的名字就够了 |
| 样板代码消除 | **Lombok**【风险·争议】 | 自动生成 getter/setter/构造器/日志对象，代码量减半 | ✅ 国内几乎标配，`@Data` 一行顶几十行<br>⚠️ 代价必须知道：① IDE 要装插件；② 它是**编译期注解处理器**（在编译阶段改抽象语法树 AST，不是反射），Java 大版本升级时偶发不兼容；③ 代码"被隐藏"，调试时对新人有迷惑性<br>📌 面试可聊的点恰好是第 ② 条——多数人只会用，说不出原理 |
| 日志 | **SLF4J + Logback**（Spring Boot 默认） | 记录运行信息 | ✅ **门面模式（Facade）**：代码只依赖 SLF4J 接口，底层实现可换，这是面试常考点；✅ 配置文件就能控制输出级别和格式<br>❌ 禁止 `System.out.println`——无法分级、无法按包控制、容器里不好收集 |
| 对象转换 | **手写 / MapStruct** | Entity（数据库对象）⇄ DTO（传输对象）⇄ VO（展示对象）的转换 | 推荐 MapStruct（编译期生成转换代码，无反射开销）。若嫌学习成本高，前期手写转换方法也完全可以接受 |
| 测试 | **JUnit 5 + Mockito + MockMvc + H2** | 自动化验证 | ✅ 全部是 Spring Boot 默认集成<br>· `@WebMvcTest` + MockMvc：不启服务器也能测接口（快）<br>· H2 内存数据库：测 SQL 不污染真实库<br>· Mockito：模拟依赖（比如测 Service 时不真查库）<br>❌ 不建议一上来上 Testcontainers（用 Docker 起真实数据库测试），配置重、本机 Docker 环境未确认 |

## 1.7 运维与部署

| 项 | 选型 | 解决什么 | 为什么选 / 为什么不选别的 |
|---|---|---|---|
| 打包 | **fat jar**（`mvn package` 产出，内嵌 Tomcat） | 把程序 + 依赖 + 服务器打成一个文件 | ✅ `java -jar app.jar` 就能跑，目标机器只需要有 JRE；✅ 这是 Spring Boot 的标准交付方式<br>📌 对比前端：`dist/` 是静态文件扔给托管平台；后端 jar 是一个**需要一直运行的进程**，两者部署性质完全不同 |
| 容器化 | **Docker**（多阶段构建） | 保证「本地能跑 = 线上能跑」 | 第一阶段用 Maven 镜像编译，第二阶段只把 jar 拷进 JRE 镜像。产物小、不受目标机环境影响。<br>⚠️ 本机 Docker 尚未确认可用，若不可用可跳过，直接传 jar 到服务器 |
| 健康检查 | **Spring Boot Actuator** | 探活（服务是否活着）+ 指标暴露 | ✅ `/actuator/health` 替代我们手写的 `/health`；✅ 企业标配，还能看 JVM 内存、线程、请求指标<br>⚠️ **生产必须限制暴露端点**（只开 health），否则 `/actuator/env` 会把配置（含密钥）泄露出去——这是真实存在的安全事故 |
| CI | **GitHub Actions** | push 时自动跑编译 + 测试 | 见 4.6 节 |

# 第二部分：五个必须拍板的决策点（含论证）

> 这一部分是全文重点。**技术栈选型的核心不是"选什么"，而是"放弃什么、以及凭什么这么放弃"**——面试时能讲出这一层的应届生极少。

## 2.1 【分歧 · 最重点】Spring Boot 3.5 还是 4.1？

### 先摆事实（已查证，截至 2026-10）

| 事实 | 内容 |
|---|---|
| Spring Boot 4.0 | 2025-11-20 发布，基于 Spring Framework 7 |
| Spring Boot 4.1.0 | 2026-06-10 发布，**当前最新的稳定线** |
| Spring Boot 3.5.x | 3.x 的**最后一条线**，最终补丁 3.5.16（2026-06-25） |
| **3.x 的开源支持** | **已于 2026-06-30 结束（EOL）**，不再有免费安全补丁 |
| Java 要求 | 3.x 和 4.x **都是最低 Java 17**；4.1 兼容到 Java 26 |
| Jackson | **Spring Boot 4 改用 Jackson 3**，包名从 `com.fasterxml.jackson` 变为 `tools.jackson` |

### 我的推荐：**Spring Boot 3.5.x**，理由四条

1. **生态兼容性是确定的。** MyBatis-Plus 对 Spring Boot 4 的支持要到 **3.5.15 版本之后才稳定**（3.5.13 刚开始提供 boot4-starter 但有问题，3.5.14 在 Boot 4 下会报 `No qualifying bean`）。而它对应的 `mybatis-plus-spring-boot3-starter` 已经打磨了两年多。
2. **knife4j 对 Boot 4 的兼容性我查不到明确结论。** 官方文档明确的是「Spring Boot 3 → 用 `-jakarta-` 坐标」，对 4.x 没有明说。对一个**没人带的新手**来说，「文档工具装不上、接口页面打不开」会直接卡死进度。
3. **你能查到的资料覆盖 3.x。** 这很现实：教程、面经、Stack Overflow、甚至 AI 的训练数据，绝大部分是 2.x/3.x。用 4.1 遇到报错，你很可能搜不到答案。
4. **企业存量最大。** 招聘 JD 里写的"熟悉 Spring Boot"，实际项目绝大多数还在 2.7 或 3.x。你讲 3.5 的经验，面试官能和你对得上话。

### 但我要把这个决策的代价说清楚（不能装作没问题）

**3.x 已经停止开源安全补丁（2026-06-30）。如果这是一个要跑三年、处理真实用户数据的生产系统，我不会这么选。**

它对你的**实际影响**有多大？分情况：

- **作为学习项目和实习作品**：影响很小。你的代码本地跑、部署在免费层，攻击面和可维护性风险都远低于真正的企业系统。
- **作为简历内容**：**必须能自圆其说**。你不能说"我不知道它 EOL 了"——那会被追问到死。你应该说：

  > "我选的是 Spring Boot 3.5，我知道 3.x 在 2026 年 6 月停止了开源支持。当时是权衡过的：MyBatis-Plus 对 Boot 4 的稳定支持刚到 3.5.15，knife4j 对 Boot 4 的兼容性没有明确结论，我是新手、需要能查到资料。升级路径是清晰的——3.x 和 4.x 共享 Java 17 基线和 `jakarta.*` 命名空间，主要工作是 Jackson 3 的包名迁移和几个 starter 换坐标。"

  **这段话本身就是加分项**——它展示了你会查依赖生命周期、会做取舍、知道升级成本在哪。比"我用了最新版"强得多。

### 什么时候应该改选 4.1？

满足**任意一条**就切换：
- knife4j 官方明确声明支持 Spring Boot 4；
- 你需要 4.x 的新特性（比如内建的 **HTTP API 版本控制**）；
- 项目要真的长期跑在生产环境。

### 切换成本（提前知道，心里有底）

| 工作项 | 成本 |
|---|---|
| MyBatis-Plus 换 `mybatis-plus-spring-boot4-starter`（≥3.5.15） | 改一行坐标 |
| Jackson 3 包名迁移 | 若你自定义过序列化配置才需要动 |
| knife4j | **未知，是最大风险点**，可能要换 fork 或降级 |
| 业务代码 | 基本不动（Spring 的向后兼容非常好） |

> **这条决策要写成 ADR-004。** 你已经有 ADR-001（依赖健康度）了，再来一篇"为什么在明知 EOL 的情况下仍选 3.5"，两篇放在一起，正好构成一条完整的「技术决策能力」证据链。

## 2.2 ORM：MyBatis 还是 MyBatis-Plus？

### 结论：**MyBatis-Plus，但必须保留写 SQL 的习惯**

**为什么不选别的：**

| 候选 | 结论 | 理由 |
|---|---|---|
| 原生 JDBC | ❌ | 手写连接、手写结果集映射，样板代码量巨大。学过一次就够，**别在项目里用** |
| MyBatis（原生） | ⚠️ 可用 | 你已经会。但分页、条件拼接都要自己写 XML |
| **MyBatis-Plus** | ✅ **推荐** | 只做增强不做改变——**它完全兼容 MyBatis 的所有写法**，你可以随时写原生 XML SQL |
| JPA / Hibernate | ❌ | 国外和部分企业主流，但**国内 Java 岗面试围绕 MyBatis 系展开的更多**；而且 JPA 把 SQL 藏起来了，你学不到索引与执行计划的直觉 |

### 选 Plus 的三个具体收益

1. **分页插件**：`Page<T>` 一行搞定，底层自动拼 `LIMIT`。不用 Plus 你得手写两条 SQL（查数据 + 查总数）。
2. **Lambda 条件构造器**：`lambdaQuery().eq(Team::getId, id)` —— 字段名写错**编译期就报错**，不用等到运行时才发现 SQL 拼错。
3. **代码生成器**：从表结构反向生成 Entity/Mapper/Service/Controller 全套代码。

### 但 Plus 有两个坑，我必须提前告诉你（这比选它更重要）

**坑一：容易把人"养废"。** 很多人用了 Plus 之后只会 `lambdaQuery()`，离开它就写不出 JOIN、不会看执行计划。而**面试恰恰考 SQL**（索引失效、慢查询、`EXPLAIN`）。

> **对策（写进项目约定）**：单表 CRUD 用 Plus；**涉及多表、聚合、复杂条件的查询，一律手写 XML SQL**。这样你既有 Plus 的效率，又没丢 SQL 能力，面试时两边都能聊。

**坑二：3.5.9 之后分页插件被拆出去了。** 分页功能依赖 SQL 解析器（jsqlparser），从 3.5.9 起不再默认打包，需要**额外引入** `mybatis-plus-jsqlparser`，且版本要和 starter 一致。不引的话分页会报类找不到。这是新手最容易卡住的地方。

### 面试能聊的点（Plus 自带的话题）

- 逻辑删除（`@TableLogic`，删数据变成 `UPDATE ... SET deleted=1`）
- 乐观锁（`@Version`，配合版本号字段解决并发覆盖）
- 自动填充（`create_time`/`update_time` 不用手动 set）

这三个都是**应届生里罕见的**——因为要真的做过项目才会遇到。做成功能，就是你的故事。

## 2.3 knife4j：三个必须知道的坑

**坑一：坐标选错会直接启动失败。**
Spring Boot 3 必须用带 `-jakarta-` 的坐标（因为 Servlet 包名从 `javax.*` 改成了 `jakarta.*`）：

```
com.github.xiaoymin : knife4j-openapi3-jakarta-spring-boot-starter : 4.5.0
```

用成不带 jakarta 的版本，会 `ClassNotFoundException`。

**坑二：生产环境必须关闭文档。**
`/doc.html` 会把你**所有接口、参数、甚至能直接发请求调试**暴露给公网。这是 Java 项目特有的安全事故高发点。

关闭方式二选一：
- 配置 `knife4j.production: true`（生产模式，文档不可访问）
- 或用 Spring Security 直接拦截 `/doc.html`、`/v3/api-docs`

**坑三：knife4j 有一个活跃 fork。**
社区出现了 `com.baizhukui:knife4j-*`（knife4j-next，当前 5.0.11），提供新 UI 和修复。原 `com.github.xiaoymin` 坐标仍在 Maven Central，可随时回退。

> 📌 这正好延续你的「依赖健康度审查」习惯：**用它之前先确认它是否还在维护、是否有 fork**。这个习惯非常值钱，继续保持。

## 2.4 鉴权：Spring Security 还是自己写拦截器？

### 结论：**Spring Security**，但只用最小配置

**自己写拦截器**（`HandlerInterceptor` + jjwt）确实更简单，半天就能跑通。**但它的面试价值接近于零**——面试官问"你怎么做鉴权的"，你说"我写了个拦截器"，然后就没有然后了。

**用 Spring Security**，你能聊的话题立刻多出一大片：

| 话题 | 一句话 |
|---|---|
| 过滤器链 | 请求进来要穿过一串过滤器，像流水线上的多道工序 |
| 认证 vs 授权 | 「你是谁」和「你能干什么」是两件事，框架里也是分开的 |
| Session vs JWT | 前者服务端存状态、依赖 Cookie；后者无状态、靠签名自证 |
| BCrypt | 慢哈希 + 自动加盐，专门对抗彩虹表 |
| CSRF | 跨域伪造请求；**用了 JWT 且不放 Cookie，天然免疫**，所以可以关掉 |

### 最小配置（避免被它的复杂度淹没）

只做三件事，其他全部关掉：
1. 关 `formLogin`（不要它自带的登录页）
2. 关 `session`（设 `STATELESS` 无状态，因为用 JWT）
3. 关 `csrf`（同上理由，用 JWT 就不依赖 Cookie）

一个自己写的 `OncePerRequestFilter`（保证一次请求只过一遍的过滤器）从请求头取 token、校验、把用户信息放进上下文，就完成了核心闭环。

## 2.5 MySQL 还是 PostgreSQL？

**选 MySQL 8.0。** 理由不是"MySQL 更好"，而是**你的目标是国内 Java 岗实习**：

- 面试考的是 MySQL：索引（B+ 树）、事务隔离级别、行锁/间隙锁、`EXPLAIN` 慢查询分析、主从。你学的每一分都直接变现。
- Java + MySQL 是国内最主流的组合，教程量级碾压。

**生产环境怎么选**：本地开发用本机 MySQL（或 Docker）；上线时用云托管 MySQL（腾讯云/阿里云都有学生优惠，几十块一个月）。如果嫌花钱，免费的 PostgreSQL（Neon）也行——**迁移成本很低**，因为 MyBatis 只是换驱动和方言。

# 第三部分：请求在 Java 后端里怎么走

## 3.1 四层结构（对应前端的分层红线）

| 层 | 职责 | 禁止做什么 |
|---|---|---|
| **Controller** | 接 HTTP 请求、取参数、返回 JSON | ❌ 不写业务逻辑；❌ 不直接碰数据库 |
| **Service** | 业务逻辑 + **事务边界** | ❌ 不感知 HTTP（不碰 request/response） |
| **Mapper** | 只写 SQL、只做存取 | ❌ 不含业务判断 |
| **Entity / DTO / VO** | 数据形状定义 | Entity 对应数据库表；DTO 是接口出入参；VO 是给前端看的 |

> 这和前端的 `views→stores→api→utils` 红线是**同一个思想**：每层只依赖下一层，方向单向。好处一样——换前端不动后端，换数据库不动业务。

## 3.2 请求旅程（一次 `/standings` 的完整路径）

1. **Servlet 过滤器链**：Spring Security 的过滤器在这层拦住请求，校验 token；跨域（CORS）也在这层处理
2. **DispatcherServlet**：Spring MVC 的总调度，按 URL 找到对应的 Controller 方法
3. **参数绑定 + 校验**：把 JSON 转成对象，执行 `@Valid` 校验规则，失败直接抛异常
4. **Controller**：调用 Service，拿结果
5. **Service**：业务处理，`@Transactional` 标注的方法在这里开启事务
6. **Mapper**：执行 SQL，HikariCP 从连接池取连接
7. **返回**：Jackson 把对象序列化成 JSON
8. **兜底**：任何环节抛异常，被 `@RestControllerAdvice` 捕获，统一转成 `{code:非0, message:错误说明}`

## 3.3 一个面试必考题：为什么 `@Transactional` 写在 Service 而不是 Controller？

三个理由，都要能说：

1. **事务的边界是业务单元，不是接口单元。** 一个业务动作可能对应多个数据库操作，Service 方法才是那个"要么全成功、要么全回滚"的原子单位。
2. **Controller 不该知道数据怎么存。** 如果 Controller 管事务，等于把持久层细节泄漏到接口层，分层就破了。
3. **有个技术陷阱**：同类内部方法调用、`private` 方法、非 public 方法上的 `@Transactional` **不生效**（Spring 的事务靠代理实现，自调用绕过了代理）。这是面试高频追问点。

> **代理（Proxy）**：Spring 不直接给你原对象，而是给一个"包装过的替身"，替身在调用前后插入事务开启/提交/回滚的逻辑。C 类比：相当于用函数指针包了一层 wrapper，在调用真实函数前后做额外动作。

# 第四部分：上线全流程（Java 版）

## 4.1 配置管理：profile + 环境变量

| 概念 | 说明 |
|---|---|
| `application.yml` | 主配置文件 |
| `application-dev.yml` / `application-prod.yml` | 按环境分开的配置，用 `spring.profiles.active` 指定用哪套 |
| 环境变量覆盖 | 运行时设 `SPRING_DATASOURCE_URL=...` 就能覆盖配置文件里的值 |

> ⚠️ **和前端的重要区别**：前端的环境变量是**构建时注入**（值被编译进产物，改了必须重新 build）；**Java 后端是运行时读取**（改了重启进程即可）。这个区别面试常考。

**绝不能进 Git 的东西**：数据库密码、JWT 密钥、云服务的 AccessKey。全部走环境变量。

## 4.2 构建与启动

```bash
mvn clean package          # 编译 + 跑测试 + 打 jar
java -jar target/app.jar   # 启动
```

对比前端：前端 `npm run build` 产出静态文件交给别人托管；后端产出的是一个**自己带服务器（内嵌 Tomcat）的可执行程序**，运行时是个常驻进程。

## 4.3 部署拓扑

| 部件 | 推荐 | 说明 |
|---|---|---|
| 前端静态文件 | **Vercel**（不变） | 自动识别 Vite，零配置 |
| 后端 jar | **腾讯云/阿里云轻量服务器**（学生优惠约 10 元/月） | Java 吃内存，免费层给 512 MB 很吃力。**花十块钱换稳定，性价比最高** |
| 备选（坚持免费） | Render / Railway 免费层 | 必须配 JVM 内存参数（见 4.4），且休眠后冷启动更慢 |
| 数据库 | 云托管 MySQL（或免费 Neon PostgreSQL） | 别用服务器本地装的 MySQL——容器/系统重装就没了 |

## 4.4 Java 特有的部署坑（Node 版没有的）

1. **JVM 看不到容器内存限制。** 老版本 JVM 会按宿主机内存来算默认堆大小，结果在容器里被 OOM（内存溢出）杀掉。Java 17 默认已开启容器感知（`UseContainerSupport`），但仍建议显式设置 `-Xmx256m`，别让它吃满。
2. **冷启动更慢。** Java 进程启动本身要几秒，加上 Spring 容器初始化，首次访问可能等 10 秒以上。**演示前务必先访问一次 `/actuator/health` 唤醒。**
3. **jar 文件较大**（通常 30–60 MB），上传和构建都比前端慢。
4. **日志必须打到标准输出（stdout）**，平台才会收集；写文件在容器里留不住。

## 4.5 安全清单（Java 版，逐条打勾）

- [ ] **`/doc.html` 生产环境已关闭**（2.3 坑二，Java 项目最常见的裸奔事故）
- [ ] **Actuator 只暴露 `/actuator/health`**，否则 `/actuator/env` 会泄露配置与密钥
- [ ] CORS 配成**白名单**（只允许你的前端域名），不要图省事放开 `*`
- [ ] 数据库密码、JWT 密钥走环境变量，**不进 Git**
- [ ] 密码用 BCrypt 存，绝不明文、绝不用 MD5
- [ ] **SQL 注入**：MyBatis 里一律用 `#{}`（预编译占位符），**禁用 `${}`**（字符串直接拼接）。这是 MyBatis 面试第一考点
- [ ] Druid 若启用，其监控页面同样要关
- [ ] Flyway 迁移脚本只做**向后兼容**的改动（加字段可以，删字段要分两步）

## 4.6 CI（持续集成）

GitHub Actions 在 push 时自动执行：

```
检出代码 → 装 JDK 17 → mvn -B package（编译 + 跑测试）→ 构建 Docker 镜像（可选）
```

加一个绿色 badge（徽章）到 README——**这东西面试官一眼就能看到，代表你的项目有工程闭环**，多数应届生项目没有。

## 4.7 上线 Runbook（按顺序打勾）

1. `mvn clean package` 本地构建通过
2. 本地 `java -jar` 启动，手动点一遍主流程
3. 确认生产环境变量已配：`SPRING_DATASOURCE_URL/USERNAME/PASSWORD`、`JWT_SECRET`、`SPRING_PROFILES_ACTIVE=prod`

# 第六部分：Java 术语速查（对照你的 C 背景）

| 术语 | 人话解释 |
|---|---|
| JDK / JRE / JVM | JDK 是开发包（含编译器）；JRE 是运行包；JVM 是真正执行字节码的虚拟机。C 类比：JDK≈编译器+标准库，JVM≈你写的程序的运行容器 |
| Maven / pom.xml | 依赖管理与构建工具。`pom.xml` 相当于 `package.json` + 构建脚本合体 |
| Maven 坐标 | `groupId:artifactId:version` 三元组，唯一确定一个库。相当于 npm 的包名 + 版本 |
| Spring / Spring Boot | Spring 是框架（提供依赖注入、事务、AOP）；Boot 是「把 Spring 配置简化」的上层封装 |
| IOC / DI（控制反转 / 依赖注入） | **你不再自己 `new` 对象**，而是声明"我需要一个 X"，容器把 X 递给你。C 类比：不用手动 `malloc` 再传指针，而是有一个全局注册表按类型给你取 |
| Bean | 被 Spring 容器管理的对象。你只管声明，生命周期归容器管 |
| 自动配置 | Spring Boot 看你引入了哪些依赖，就猜你想要什么配置并自动配好。这是它"开箱即用"的来源 |
| starter | 一组预打包的依赖集合，引入一个 starter 等于引入一整套兼容版本的库 |
| AOP（面向切面编程） | 在不改原函数的前提下，统一在前后插入逻辑（日志、事务、鉴权）。C 类比：相当于给一堆函数统一套一层 wrapper，但不用手写 |
| 代理（Proxy） | Spring 给你的不是原对象，是包了一层的替身。事务、`@Transactional` 就靠它实现 |
| ORM | 数据库表和对象之间的自动映射。你操作对象，框架帮你生成 SQL |
| 连接池 | 预先建好一批数据库连接放着复用。建连接很贵（握手、鉴权），不能每次请求都新建 |
| fat jar | 把程序 + 所有依赖 + 内嵌服务器打成一个 jar，直接 `java -jar` 就能跑 |
| 内嵌 Tomcat | 服务器被打包进 jar 里，不需要外部装 Tomcat。Node 类比：Express 自己就是服务器，Java 以前要额外装 Tomcat，Boot 把它塞进来了 |
| 迁移（migration） | 表结构变更的版本化脚本，可执行、可追溯、绝不手动改线上表 |
| 探活 | 平台定期访问 `/actuator/health` 判断服务是否活着，死了自动重启 |
| OOM | 内存溢出，进程被系统杀掉。Java 部署最常见的事故 |
| 无状态容器 | 一次性盒子，随时被销毁重建，写进本地磁盘的东西会丢 |
| 冷启动 | 服务休眠后首次请求要重新拉起进程，Java 比 Node 慢得多 |
| 门面模式（Facade） | 只依赖一个统一接口，底层实现可替换。SLF4J 就是日志界的门面 |
