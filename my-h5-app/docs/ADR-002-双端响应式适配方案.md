# ADR-002：PC / 移动双端适配方案选型

> **⚠️ 修订（2026-10-05）**：项目定位由「手机为主、兼顾 PC」调整为「**PC 浏览为主、兼顾手机**」。
> 因此：① 前端组件库由 **Vant（移动端）改为 Element Plus（桌面）**；② 移除 `postcss-px-to-viewport-8-plugin`，不再做 px→vw 等比缩放，改为真实像素 + `responsive.css` 限宽居中；③ 下拉刷新等触摸手势改为按钮刷新。下方「选 B 响应式」的原始决策保留作历史。新落地见 `responsive.css` 与 `App.vue`（el-menu 导航）。

- **状态**：已采纳（2026-10-04），2026-10-05 修订为「PC 为主」
- **决策人**：项目组（两人团队）
- **相关**：ADR-001 移动端适配方案（vw 插件选型与其停更风险）

---

## 一、背景

项目最初定位是**移动端 H5**，采用「375 设计稿 + px 自动转 vw」方案。现提出要同时支持 PC 浏览。

先明确问题有多严重：vw 是**视口单位**，设计稿上 18px 的标题被转成 `4.8vw`，在 1920px 宽的显示器上会渲染成 **92px**。整个页面等比放大 5 倍，布局不崩，但视觉上是"老年机模式"。

**一个必须先破除的直觉**：有人会想"给容器加 `max-width` 不就行了"。**不行**——vw 算的是视口宽度，不是父容器宽度。容器卡成 420px，里面的元素照样按 1920px 计算然后溢出。所以这件事只能在**适配方案层面**解决，纯 CSS 补丁无效。

## 二、候选方案

| 方案 | 做法 | 改动量 | 手机端风险 | Vant 兼容性 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| **A 手机壳** | PC 上居中显示手机宽度内容，两侧留白 | 1 处配置 | 零 | 无问题 | PC 上"能看就行" |
| **B 响应式** | 同一套页面，断点内用固定像素重新排版 | 每个页面补断点 | 中 | 有摩擦（见"已知代价"） | 一套代码通吃两端 |
| **C 双端分离** | PC 独立一套页面组件，按屏宽分发路由 | 每个页面写两遍 | 零 | 无问题（PC 换组件库） | 两端都是正式形态 |

## 三、决策

**选 B（响应式自适应），全项目统一改。**

### 决策理由

1. 需求是"PC 也要能用"，不是"PC 上凑合看一眼"，A 方案的信息密度在宽屏上太低。
2. C 方案对两人团队工作量翻倍，且现阶段没有 PC 专属设计稿，写两遍等于凭空设计一套 UI。
3. B 方案的改动**与 A 不冲突**：将来若发现 PC 体验仍不够，可以在断点内继续加宽屏布局，不必推倒重来。

### 我原本的推荐与分歧说明

架构角度我原本推荐 A（投入产出比更高，且顺手解决 ADR-001 的停更依赖）。决策人选择 B，理由是产品要真正的 PC 体验。**这个选择是合理的**，但要清楚 B 的代价是：每个新页面都要写一段断点样式，属于长期维护成本。

## 四、实现机制：一条配置撑起两套逻辑

核心是 `vite.config.ts` 里的 **`mediaQuery: false`**（该项目一开始就有，但当时没意识到它是双模式的关键）：

```
默认样式（媒体查询外）        → px 转 vw    → 移动端等比缩放，手机端零改动
@media (min-width: 768px) 内  → px 保持固定 → PC 端用真实像素接管排版
```

这解决了 ADR-001 里遗留的那个问题——纯 vw 在宽屏无限放大。隔离之后：手机端继续自动适配，PC 端写固定像素，互不干扰。

同时新增 `.pc-fixed` 进入 `selectorBlackList`，作为"永远按写的 px 渲染"的逃生通道。

### 断点规范（全项目统一，禁止页面自创断点）

| 区间 | 形态 | 单位策略 |
| --- | --- | --- |
| < 768px | 手机 | px → vw，等比缩放 |
| ≥ 768px | 平板 / PC | 固定 px，重新排版 |

**只用一个断点是刻意的取舍**：每多一个断点，要维护的布局分支是乘法关系，这是响应式最容易失控的地方。将来若确实要区分平板与桌面，**在 `responsive.css` 里加**，不要散到页面。

### 文件分工

| 文件 | 职责 |
| --- | --- |
| `src/assets/styles/responsive.css` | **全局**断点规则：背景、内容区限宽居中、Vant 组件尺寸微调 |
| 各页面 `<style scoped>` 末尾的 `@media` | **本页**专属的 PC 排版（字号、间距、列宽、hover） |

为什么全局和页面要分开：断点值和容器宽度是全项目统一决策，散到各页面就会出现"A 页 768、B 页 800"的混乱。

## 五、已知代价与限制（必须知道）

1. **Vant 是移动端组件库**。默认按触屏设计（44px 触控区、14px 字号），PC 上偏紧凑；更关键的是 `van-pull-refresh` 依赖触摸手势，**鼠标拖不动**。已在积分榜页加 PC 专用刷新按钮作为替代入口。将来若 PC 成为主战场，应换 Element Plus 或 Naive UI。
2. **hover 只能写在断点内**。手指没有"悬停"概念，写在断点外会让手机端点完一行高亮残留不走。
3. **新增页面必须同步写断点**，否则该页在 PC 上就是放大 5 倍的手机页。见下方 checklist。
4. **构建器会改写媒体查询语法**：产物中出现的是 `@media (width>=768px)`（Media Queries Level 4 范围语法），而非源码里的 `min-width`。这是 CSS 压缩器的优化，**Safari 16.4 以下不识别**——降级行为是忽略该媒体查询、显示移动端样式，不会崩，但 PC 样式不生效。当前浏览器覆盖率足够，若将来要兼容旧 Safari，需在 `build.cssMinify` 或 target 配置里关掉这个转换。

## 六、回滚方案

改动集中在三处，可整体回退：

1. 删 `src/assets/styles/responsive.css` 及 `main.ts` 中的 import
2. 删三个页面 scoped 样式末尾的 `@media` 块
3. `vite.config.ts` 的 `selectorBlackList` 去掉 `.pc-fixed`

回退后项目恢复为纯移动端 vw 方案，不影响任何业务逻辑。

## 七、新页面 PC 适配 checklist

写完一个页面后，把浏览器拉宽到 ≥768px 逐项核对：

- [ ] 字号是不是回到了合理区间（不是被 vw 放大的巨型字）
- [ ] 内容区有没有被限宽居中（由全局 `#app` 保证，除非本页需要更宽）
- [ ] 列表行有没有 hover 反馈（且只在大屏生效）
- [ ] 有没有只存在于手机的操作（下拉刷新、滑动删除）需要给 PC 替代入口
- [ ] 按钮有没有被拉成整行横幅（用 `max-width` 收住）

## 八、方法论沉淀

**评估一个适配方案，问三件事：**

1. 它解决的是"缩放"还是"布局"？——vw/rem 解决缩放，媒体查询解决布局，两者不能互相替代。
2. 逃生成本多高？——要不要在业务代码里写它的 API？本项目这套方案只活在配置和 CSS 里，业务组件完全不知道它的存在。
3. 断点由谁维护？——必须收敛到单一文件，否则必然失控。
